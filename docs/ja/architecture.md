# Harumi アーキテクチャ

> 初期設計メモ: この文書は当初のアーキテクチャ方針を残したものです。
> 現在の利用コマンドと対応インポートについては `README.ja.md` と `harumi --help` を正としてください。

## 目的

Harumi は、あいまいな自然言語の指示から、ローカル PC 上のファイルやフォルダを見つけるためのローカルファーストなアシスタントです。

ユーザーが指定したディレクトリを走査し、文書やソースコードからテキストを抽出し、正規化済みテキスト、要約、検索用インデックスを保存します。検索結果としては、候補ファイルとその理由を返します。

主な要求:

- ローカルの文書とソースファイルを索引化する
- Microsoft MarkItDown で対応文書形式を Markdown に変換する
- Ollama 経由のローカル LLM で要約を生成する
- メタデータ、Markdown、要約、検索インデックスをローカルに保存する
- 「昨年冬ごろの税金設定のメモ」や「スクショを S3 に送るスクリプト」のようなあいまい検索を扱う
- ファイル更新時に差分再インデックスできる

初期版でやらないこと:

- 無設定で PC 全体を自動索引すること
- 完璧な OCR やすべてのバイナリ形式への完全対応
- マルチユーザー対応
- リモート同期

## プロダクトの位置づけ

Harumi は「文書チャット」よりも「個人向け検索エンジン」に近いアプリです。

AnythingLLM は近い領域にありますが、主眼は選択した文書に対するワークスペース型チャットです。Harumi が必要とするのは次です。

- ファイル単位で永続化されるインデックス
- 安定したローカルメタデータ保存
- 差分更新
- ファイルやフォルダの発見を主目的とした検索
- チャットの文脈よりも、検索補助としての要約

## 推奨スタック

### 言語

- Python 3.11+

理由:

- ファイル処理系のエコシステムが強い
- MarkItDown と Ollama を扱いやすい
- MVP には十分な速度である

### コアライブラリ

- `markitdown`
  - Office、PDF、HTML などの対応形式を Markdown に変換
- `ollama`
  - ローカルモデルによる要約と埋め込み生成
- `sqlite3`
  - メタデータと正規化済みテキストの保存
- `SQLite FTS5`
  - ファイル名、パス、本文、要約の全文検索
- SQLite テーブル
  - 現在の実装では embedding vector を JSON として保存
- `watchdog`
  - 将来のファイル監視
- `python-magic`
  - MIME 判定
- `argparse`
  - CLI
- `fastapi`
  - 将来のローカル API
- `pydantic` と `pydantic-settings`
  - 型付き設定管理

### なぜハイブリッド検索が必要か

ベクトル検索だけでは不十分です。

- 全文検索は、正確な名前、拡張子、記号、パス断片に強い
- ベクトル検索は、あいまいな要求や言い換えに強い
- 実用的な精度には両方の組み合わせが必要

## システム構成

主なコンポーネント:

1. Scanner
   - 指定ルートを巡回する
   - ファイルメタデータを収集する
   - 無視ルールや非対応ファイルを弾く

2. Normalizer
   - ファイル形式に応じて処理を振り分ける
   - 文書形式は MarkItDown を使う
   - コードやプレーンテキストは直接読む
   - すべてを検索可能なテキストへ正規化する

3. Chunker
   - 長文を埋め込みや詳細検索向けに分割する

4. Summarizer
   - Ollama で文書要約を作る
   - ソースコード群については、将来的にフォルダ単位またはプロジェクト単位の要約を優先する
   - 要約文とメタ情報を保存する

5. Indexer
   - メタデータ、正規化テキスト、チャンク、要約、埋め込みを保存する
   - 全文検索とベクトル検索の索引を維持する

6. Search engine
   - クエリを埋め込みへ変換する
   - FTS とベクトル検索を実行する
   - ヒューリスティックで再ランキングする

7. Assistant layer
   - 候補ファイルと理由を返す
   - 埋め込みだけに頼らない説明可能な結果を返す

8. Activity importers
   - ブラウザ履歴を activity event / session として取り込む
   - ChatGPT、Claude、Gemini のエクスポートを AI activity として取り込む
   - 取り込んだ activity を worklog / retrospect に利用する

## データフロー

1. ユーザーがインデックス対象ルートを設定する
2. Scanner がファイルを見つけてメタデータを取る
3. Router が変換方法を選ぶ
4. 本文を Markdown またはテキストへ正規化する
5. ハッシュを確認して重複処理を避ける
6. 新規または更新ファイルに対して要約を生成する
7. チャンクと埋め込みを生成する
8. メタデータ、本文、ベクトルを保存する
9. 必要に応じてブラウザ履歴と AI エクスポートを activity として取り込む
10. クエリ時に全文検索と意味検索を組み合わせる
11. ランキング済みのファイル・フォルダ結果を返す

## ファイル形式の扱い

### MarkItDown を使うもの

- PDF
- Word、PowerPoint、Excel
- HTML
- CSV など Markdown 化の恩恵がある文書系形式
- 対応していればメールやアーカイブ形式

### 無理に MarkItDown に通さないもの

- ソースコード
- 小さなプレーンテキスト
- 設定ファイル
- JSON、YAML、TOML

コードや設定は生テキストのほうがよい理由:

- 構造が重要
- 行単位の検索が重要
- Markdown 化の利得が小さい

また、意味検索のためにコードをファイル単位で要約するのは、長期的にはあまり効率がよくありません。将来的な方針としては次を想定します。

- コード本文は生テキストのまま検索できるように保つ
- 意味検索向けの要約はフォルダ単位またはプロジェクト単位で作る
- `pyproject.toml`、`package.json`、`go.mod`、`Cargo.toml` などを境界検出に使う
- コード寄りクエリでは、その上位単位の要約を強く使う

## 保存設計

アプリ専用ディレクトリ配下にローカル保存する想定です。

```text
~/.local/share/harumi/
  config.toml
  harumi.db
  cache/
    normalized/
    summaries/
  logs/
```

主要テーブル:

- `roots`
- `files`
- `documents`
- `summaries`
- `chunks`
- `query_history`

全文検索用:

- `fts_documents`

ベクトル保存:

- 現在はファイル・フォルダ単位の embedding を SQLite に JSON 配列として保存
- クエリ時に Python で cosine similarity を計算
- SQLite JSON vector が遅くなったら、将来的に専用のローカル vector store を検討する

## 検索設計

扱いたい検索の例:

- トピック検索
  - 「請求書パーサのメモ」
- 作業記憶検索
  - 「税金支払い設定のファイル」
- コード探索
  - 「スクショをアップロードするスクリプト」
- フォルダ探索
  - 「古い旅行書類の置き場所」
- 時期指定
  - 「1月ごろ編集した文書」

検索段階:

1. クエリ解析
   - ファイル名っぽい語、日付、コード意図、フォルダ意図を検出
2. 全文検索
   - パス、ファイル名、要約、本文を検索
3. ベクトル検索
   - クエリ埋め込みと summary/chunk 埋め込みを比較
4. 再ランキング
   - ファイル名一致、パス一致、更新日時、ファイル種別意図を加点
5. 結果説明
   - 要約、パス、ヒット理由を返す

## 要約戦略

各ファイルに対して 2 種類の要約を持つ方針です。

- `summary_short`
  - 結果一覧向けの 1〜3 文
- `summary_long`
  - 検索と精査向けの詳細要約

大きなファイルでは、先に部分要約を作ってからファイル全体要約へまとめる方法を取れます。

## モデル戦略

Ollama をすでに使っている前提で、用途ごとにモデルを分けます。

- 要約モデル
  - 圧縮性能と速度のバランスがよい instruct 系
- 埋め込みモデル
  - embedding 専用モデル

実務上の注意:

- 最大モデルを常時使わない
- 索引処理では最高精度よりスループットが重要

## 無視ルール

最初から明示的な ignore 設定が必要です。

標準除外候補:

- `.git/`
- `node_modules/`
- `.venv/`
- `venv/`
- `dist/`
- `build/`
- `.cache/`
- OS メタデータ系
- サイズ制限を超える巨大ファイル

## 差分インデックス

毎回すべてを再処理しません。

再処理条件:

- 新規ファイル
- `mtime` 変更
- サイズ変更
- 内容ハッシュ変更
- 要約プロンプト変更
- モデル変更時の明示的再構築

推奨:

- まず `mtime` とサイズで軽く判定
- 必要時だけハッシュを計算

## セキュリティとプライバシー

- ユーザーが明示したルートだけ索引する
- 機密ディレクトリは除外可能にする
- 要約済みか索引のみかを記録する
- 外部送信は行わない
- ローカルモデルだけを使う
- エラーログに機密本文を丸ごと残さない

## MVP の範囲

MVP で必要なもの:

- ルート設定
- 再帰スキャン
- 文書正規化
- コードとテキストの直接読込
- 短い要約と長い要約の生成
- SQLite 保存
- FTS 索引
- ファイル単位 embedding
- `harumi find "税金のメモ"` のような CLI 検索
- 上位候補と理由の表示

MVP で除外するもの:

- OCR
- GUI
- リアルタイム監視
- 端末間同期
- chunk 単位の厳密引用
- 自律エージェント動作

## 推奨実装順

1. Python プロジェクト初期化
2. SQLite スキーマ作成
3. ルート管理とスキャナ
4. MarkItDown による正規化
5. Ollama による要約
6. FTS5 検索
7. embedding とベクトル検索
8. ハイブリッド再ランキング

## 結論

このアプリは十分に実現可能です。

最初の構成としては次が適切です。

- Python
- MarkItDown
- Ollama
- SQLite FTS5
- LanceDB

これで、重い分散構成や大きな GUI を先に持ち込まずに、ローカルファーストな MVP を素直に検証できます。
