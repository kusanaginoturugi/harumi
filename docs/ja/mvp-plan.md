# Harumi MVP 計画

## 目的

選択したディレクトリを索引化し、ファイル内容を検索可能テキストへ正規化し、Ollama でローカル要約を作り、あいまいな自然言語クエリから候補ファイルを返せるローカルファーストなアシスタントを作る。

MVP でまず証明したい流れ:

1. ファイルを走査する
2. 内容を正規化する
3. ローカルモデルで要約する
4. メタデータと本文を保存する
5. ハイブリッド検索する
6. 役に立つ結果を返す

## MVP の範囲

### 含めるもの

- ユーザーが指定したルートディレクトリ
- 再帰スキャン
- ignore ルール
- MarkItDown による文書正規化
- ソースコードとテキスト系ファイルの直接読込
- SQLite へのメタデータ保存
- SQLite FTS5 による全文検索
- Ollama によるローカル要約
- Ollama によるファイル単位 embedding
- LanceDB によるベクトル検索
- `scan`、`reindex`、`find` の CLI
- 検索結果の理由表示

### 含めないもの

- OCR
- リアルタイム監視
- GUI
- PC 全体の自動索引
- クラウド同期
- マルチユーザー
- 複数ファイル横断 QA
- アプリからの直接編集やオープン

## ユーザーストーリー

主なもの:

- ルートディレクトリを登録できる
- スキャンして件数を確認できる
- あいまいな検索で候補を得られる
- なぜその結果が返ったか分かる
- 変更のないファイルを再処理せずに再インデックスできる

補助的なもの:

- 名前一致、パス一致、本文一致、意味一致のどれが効いたか分かる
- ルートやファイル種別で絞り込める

## 想定コマンド

```text
harumi init
harumi roots add /path/to/root
harumi roots list
harumi scan
harumi scan --root /path/to/root
harumi find "税金設定のメモ"
harumi find "スクショをアップロードするスクリプト" --type code
harumi status

# 作業記録（実装済み）
harumi worklog                          # 今日の変更ファイルをまとめる
harumi worklog --date yesterday         # 昨日
harumi worklog --no-llm                 # ファイル一覧のみ
harumi retrospect 2026                  # 年単位
harumi retrospect 202604                # 月単位
harumi retrospect 20260430              # 日単位
```

## 機能要件

### FR-1 ルート管理

- ルート追加
- ルート有効/無効
- ローカル永続化

受け入れ条件:

- プロセス再起動後もルート一覧が残る

### FR-2 スキャン

- 有効なルートを再帰走査
- ファイルメタデータ取得
- 抽出前に ignore 適用

受け入れ条件:

- 発見、無視、索引対象、未変更、失敗の件数が分かる

### FR-3 正規化

- MIME と拡張子で処理分岐
- 文書は MarkItDown
- コードやテキストは直接読込
- 正規化済み本文を保存

受け入れ条件:

- PDF、DOCX、HTML、MD、TXT、PY、TS、JS、JSON、YAML、TOML を扱えるか、明示的にスキップされる

### FR-4 要約

- 文書系ファイルに対して Ollama で要約を生成する
- モデル名とプロンプト版を保存する
- ソースコードは本文検索を優先し、上位単位のコード要約は後段フェーズへ回す

受け入れ条件:

- 未変更ファイルでは要約を再生成しない
- 短すぎるファイルやコードファイルは方針に応じて要約を省略できる

### FR-5 Embeddings

- ファイル要約ごとに 1 つ embedding を作る
- ローカルベクトルストアへ保存

受け入れ条件:

- クエリ埋め込みと類似検索から再ランキング候補を得られる

### FR-6 全文検索

- パス、ファイル名、正規化本文、要約を FTS5 へ入れる

受け入れ条件:

- 正確なファイル名やパス検索で期待結果が上位に出る

### FR-7 ハイブリッド検索

- FTS とベクトル検索を組み合わせる
- ファイル名/パス一致などのヒューリスティックで再ランキングする

受け入れ条件:

- 小規模な実データで、あいまい検索でも上位数件に有用な結果が含まれる

### 将来のコード検索拡張

- `pyproject.toml`、`package.json`、`go.mod`、`Cargo.toml` などを使ってプロジェクト境界を検出する
- コードの意味要約はファイル単位ではなく、フォルダ単位またはプロジェクト単位で作る
- コード寄りクエリでは、その上位単位の要約を活用して検索精度を上げる

### FR-8 説明可能な出力

各結果に対して次を出す:

- ファイルパス
- ファイル種別
- 短い要約
- スコア
- ヒット理由

受け入れ条件:

- DB を直接見なくても、なぜ出てきたか分かる

## 非機能要件

- ローカルファースト
- インデックス作成と検索にネットワーク必須を持ち込まない
- 個人 PC で現実的な速度
- 失敗したファイル単位で回復可能
- 1 ファイル失敗で全体が落ちない

- `fts_documents`

## クエリ処理

1. 生の検索クエリを受け取る
2. 意図を推定する
   - コードか文書か
   - ファイル名やパス断片らしき語
   - 時期指定
3. FTS 検索
4. embedding 検索
5. 候補統合
6. ヒューリスティックで再ランキング
7. 理由つきで返す

## マイルストーン

### Milestone A: Scanner のみ

目標:

- ルート走査とメタデータ保存

使えるコマンド:

- `harumi init`
- `harumi roots add`
- `harumi roots list`
- `harumi scan`

### Milestone B: 検索可能テキスト

目標:

- 正規化と FTS 検索

使えるコマンド:

- `harumi find "keyword query"`

### Milestone C: 意味検索

目標:

- 要約、embedding、ハイブリッドランキング

使えるコマンド:

- `harumi find "vague natural language query"`

## リスク

### リスク 1: 初手で対象が広すぎる

対策:

- 明示ルート登録を必須にする
- 強めの標準 ignore を持つ

### リスク 2: ローカル要約が遅い

対策:

- 小さめのモデルを使う
- 変更ファイルのみ要約する
- まずはファイル単位要約だけにする

### リスク 3: 検索品質が低い

対策:

- ハイブリッド検索にする
- 理由表示を必須にする
- 小規模実データで先に調整する

### リスク 4: 文書変換失敗

対策:

- ファイル単位で失敗を隔離する
- DB に失敗状態を残す
- 非対応ファイルは明確にスキップする

## 最初のテスト用コーパス

いきなり PC 全体ではなく、小さいが実用的なコーパスで始める。

含めたいもの:

- PDF 数本
- Word 文書数本
- Markdown ノート
- ソースコードリポジトリ
- 設定ファイル
- HTML エクスポート

このコーパスで調整するもの:

- ignore ルール
- 要約プロンプト
- ランキング重み
- ファイル種別の振り分け

## 直近の推奨

最初は基盤だけ進める。

1. Python プロジェクトを作る
2. DB スキーマを作る
3. ルート管理とスキャンを入れる

embedding から始めない。

最短で価値が出る順番は次:

- メタデータ
- 正規化本文
- FTS
- 要約
- ベクトル検索
